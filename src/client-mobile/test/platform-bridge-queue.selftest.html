Covers docs/plans/runtime-platform-descriptors.md §5 DoD#12's "same-turn" case, §5 DoD#13, the per-candidate tick-budget semantics of §3.1, and the §3.1a post-app.js-load give-up path — all impossible to reproduce against the real obsidian-mobile bundle from outside (app.js's own module-level code runs the real Object.defineProperty('Platform', ...) call and its own `load` event, so we can't inject a second same-turn candidate ahead of it, nor control exactly when it "loads"). No app.js is loaded on this page at all — each scenario runs platform-bridge.js fresh inside its own iframe so state never bleeds between them; Scenarios C/D simulate app.js's `load` signal by calling window.__owPlatformBridge.notifyAppJsLoaded() directly, the same hook boot.js calls for real.

calev (round 2 of the fix pass) found two labels here that promised more than the test actually proved: Scenario A's old per-candidate assertion added both candidates in the SAME synchronous turn, so their tick counts could never diverge — a shared/global budget would have passed the exact same assertion. And the old Scenario C only exercised notifyAppJsLoaded()'s OWN immediate empty-queue check, never pump()'s separate post-load queue-drain branch (the one finding 2 of the previous round actually added). Scenario A below now makes the real candidate join the queue LATE — after the stuck sibling already has ticks of its own on the books — which is the only way divergent per-candidate budgets can be observed at all. Scenario D is new and drives an in-flight candidate through pump()'s post-load drain branch specifically.
